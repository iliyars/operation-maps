# Roadmap до v1.0

Дата пересмотра: 2026-11-05. Основание: текущий рабочий код, включая
незакоммиченные изменения, тесты и документы проекта.
Предыдущий roadmap сохранён в [истории](docs/roadmap-history-2026-11-05.md).
Подробности проверки — в [аудите](docs/code-audit-2026-11-05.md).

## Что считаем финалом

v1.0 — стабильное Windows-приложение для текущей команды: инженер берёт
реальный ПЭ3 XML, сопоставляет компоненты, дополняет справочник, вводит
условия и значения, сохраняет проект и получает проверенный комплект Word.
Повторное открытие проекта сохраняет принятые инженерные решения; изменение
справочника не меняет выпущенный комплект без явного обновления проекта.

Граница релиза — согласованный перечень реально нужных форм и исходных
форматов. Наличие десятков описаний форм в сидере не означает их поддержку
в готовом продукте. Полный охват всех бланков и коммерческий продукт —
отдельные цели после v1.0.

Это предлагаемый технический план. Состав обязательных форм, правила
инженерных расчётов и приёмку печатного документа подтверждает владелец
проекта. Пока они не согласованы, нельзя обещать дату завершения.

## Исходное состояние

- Четыре проекта: Domain → Application → Infrastructure и Wpf.
  WPF использует EF Core и инфраструктуру напрямую; функциональные модули
  уже выделены, переписывание архитектуры целиком не требуется.
- Реализованы XML/Word-импорт, сопоставление, справочник и администраторы,
  собственные формы, примечания и облегчённый режим, split/merge,
  undo/redo, JSON-проекты .omaps v4 (чтение v1–v3), аварийные копии, проверка перед
  экспортом, титул, содержание, сквозная нумерация и сборка одного Word.
- Сидер регистрирует 72 формы. В ресурсах 14 комплектов template.docx +
  map.json: 3, 4, 55, 56, 58, 60, 64, 67, 68, 69, 75, 77, 83, 86.
  Форма 3 строится отдельно; количество записей каталога с ресурсами
  нельзя напрямую сравнивать как процент готовности.
- Release-проверка диалогов приложения: **449 passed, 0 failed,
  0 skipped**, nullable-диагностика считается ошибкой; предупреждений нет.
  Проверка выполнена в `artifacts/merge-verification`: обычная Release-папка
  занята запущенным приложением. Это не приёмка поставки или пагинации в Word.
- Windows CI есть в `.github/workflows/windows-ci.yml`;
  первый удалённый прогон ещё нужно проверить. Portable-публикация есть в publish.ps1.

## R2 — Проект как воспроизводимый инженерный документ

Сейчас .omaps хранит пользовательский ввод, но повторно сопоставляет
компоненты и читает НТД из текущего каталога. Это сознательное прежнее
поведение, которое нужно изменить для воспроизводимого выпуска.

- [ ] Ввести новую версию .omaps со снимком используемых данных: формы и
  параметры, НТД семейства/компонента, выводы, пояснения, выбранные условия,
  база коэффициента нагрузки и идентификация источника/версии шаблонов.
- [ ] Открывать новый формат из снимка; недоступный каталог или удалённый
  компонент не должны уничтожать сохранённые данные проекта.
- [ ] Добавить явную команду «Обновить из справочника» с просмотром различий,
  конфликтов и подтверждением применения. Сохранить измеренные значения,
  разбиение столбцов и пользовательские примечания.
- [ ] Мигрировать v1–v4: сохранить всё имеющееся; если старый файл не
  содержит НТД, явно показать восстановление по текущему каталогу и
  необходимость проверки. Прошлые значения не выдумывать.
- [ ] Учитывать изменения RowNumber/состава параметров: не переносить
  значения молча в другую смысловую строку. Определить стабильные ключи.
- [ ] Проверить dirty/revision, автокопию и восстановление для каждого вида
  редактирования, смены проекта и незавершённого сохранения.

Критерий завершения: новый сохранённый проект после изменения/удаления
каталожной записи воспроизводит прежние данные экспорта. Обновление НТД —
отдельное действие с проверяемым результатом. Старые файлы открываются
без молчаливой потери содержимого.

## R3 — Импорт и справочник без ручного обхода ограничений

- [x] Явно диагностировать неподдерживаемую структуру/кодировку XML,
  пропущенные строки, пустые и повторяющиеся позиции. Не терять строки
  только из-за нераспознанного типа; показывать результат разбора.
  Кодировка определяется объявлением XML/BOM (Windows-1251, UTF-8,
  UTF-16 проверены); без одного RecordsData документ отвергается без
  замены текущего проекта. Неизвестный тип сохраняется для сопоставления;
  предупреждения с номерами записей показываются после импорта.
  Восемь реальных перечней проходят без изменения количества строк/позиций.
  Правила: [docs/xml-import.md](docs/xml-import.md).
- [x] Сопоставление: точное совпадение → однозначная нормализация →
  ручное решение. Проверить похожие обозначения и неоднозначности;
  нормализация не должна объединять разные компоненты.
  Точное имя компонента/семейства имеет приоритет даже при коллизии
  нормализованных ключей. Несколько кандидатов не выбираются автоматически;
  неоднозначное семейство теперь явно перечисляет варианты в предупреждении,
  сохраняя известный тип и не присваивая чужие формы. Проверены оба порядка
  семейств, номиналы, допуски, единицы/регистр и признаки ОС/ОСМ.
  Исходное обозначение сохраняется для UI и Word; каталог не переписывается.
- [ ] Повторный импорт Word: показывать различия существующего компонента
  и давать обновление выбранных полей без удаления записи и смены Id.
  Отдельно показывать расхождение общих данных семейства.
- [x] Одна транзакция на создание компонента, включая новый тип,
  семейство, НТД, выводы, примечания и условия. Создание типа перенесено
  из Word-импорта в `ComponentEntryService`; существующий тип используется
  повторно, принадлежность семейства выбранному типу проверяется.
  Проверены ошибка до записи, поздняя ошибка примечания, полный откат,
  повторная попытка и отмена после промежуточного сохранения компонента.
- [ ] При добавлении обновления существующих компонентов обеспечить
  ту же транзакционность для всех изменяемых данных.
- [x] Сохранить текущую семантику пакетной отмены: завершённые компоненты
  остаются, текущий не сохраняется частично; результат явно перечисляется.
  Сквозная проверка отката использует реальный SQLite и отмену после
  сохранения текущего компонента; UI-проверки покрывают итог и продолжение.
- [x] Сохранить правило облегчённого режима, неизвестное основное значение
  и обязательный текст вместе со значением; проверить повторные слоты,
  конфликтующие варианты и неоднозначные/непривязанные маркеры Word.
  Неизвестный/неоднозначный маркер не удаляется из исходного значения.
  Разные определения одного маркера, непривязанные определения и текст
  без маркера видны в окне импорта и блокируют только проблемный компонент
  до исправления Word. Ошибка последующего слота не теряется; разные
  собственные формы одного компонента явно диагностируются.
  Проверены исправление/повторный импорт, отдельное хранение условного
  значения и сохранение пометки отсутствующего нормального значения.
  Температурные диапазоны и база Кн в скобках не считаются сносками.
  Правила: [docs/word-import-notes.md](docs/word-import-notes.md).
- [x] Требование Ильи: один параметр может иметь несколько значений
  по режимам (например, ресурс 100000 ч в нормальном и 150000 ч
  в облегчённом). Значения хранятся отдельно и не заменяют друг друга.
  Если облегчённое значение есть, а нормального нет/оно неизвестно,
  компонент помечается «Необходимо редактирование» с перечнем параметров:
  в проекте, списке/карточке справочника и проверке экспорта.
  Проверка действует и для необязательных параметров и ранее проверенных
  записей; выбор облегчённого режима её не снимает. Подтверждение
  администратором запрещено до заполнения нормального значения.
  После исправления пометка пересчитывается; миграция БД не требуется.
- [x] Проверить «не проверен» для всех путей добавления: проект с новым
  и существующим семейством, импорт Word с новым типом, администратор
  через справочник с новым и существующим семейством.
  Проверены сохранённый флаг, очередь/счётчик, карточка, запрет подтверждения
  обычному пользователю и снятие флага администратором через UI-команду.
  Новые проектные/Word-записи требуют проверки; добавленные в справочник
  администратором проверены сразу. Повторная реализация флага не понадобилась.
- [x] Довести неизвестный тип XML до ручного заполнения: мастер проекта
  предлагает существующие типы, если исходный тип пустой или отсутствует
  в каталоге. До выбора переход заблокирован, исходное имя сохраняется;
  созданный компонент попадает в очередь проверки, как остальные.
- [ ] Дать администратору редактировать примечания, условные значения,
  собственную форму и принадлежность семейства с проверкой зависимостей.
  Удаление/повторное создание не должно быть штатным способом исправления.

Критерий завершения: Word → каталог → XML → проект → Word проходит на
эталонах; повторный импорт управляемо обновляет данные без дублей;
ошибка/отмена не оставляет частично созданный компонент.

  не удаляется предварительно. Проверены создание/замена, отмена,
  занятый файл и повторная попытка, конкурирующие записи и уборка
  временных файлов; чужой временный файл не затрагивается.
- [x] Проверять физическую геометрию map.json относительно template.docx:
  таблицу, существование ячеек, пересечения метаданных/значений/подписей/
  примечаний/условий и слотов, отдельные колонки НТД/схемы/выводов,
  привязку дополнительной строки к основной и её слоты.

  с конкретной диагностикой. Проверка шаблонов в UI выполняется в фоне.

  Физически корректные координаты сами по себе не доказывают, что значение
  попадает в нужную смысловую строку ГОСТ-бланка.
- [ ] Для каждой обязательной формы: каждый слот, пустой последний слот,

## Как вести этот план

Работать небольшими завершёнными задачами: воспроизводимый пример →
изменение → проверка → документация → критерий этапа. Галочку ставить
по проверенному результату, не по наличию класса или кнопки.
Оценки срока давать после R0 и уточнять после R1/R2; процент готовности
по числу тестов или строк кода не использовать.
